# Фича: "Свой пресет" — конструктор-микс из существующих пресетов

> **Статус: реализовано** (см. `index.md`, раздел 0 — сводка изменений
> и точные имена методов/файлов в актуальном коде). Этот файл остаётся как
> проектный документ решения — архитектура и обоснование ниже соответствуют
> тому, что реализовано.
>
> Источник идеи: `index.md`, раздел 11.3.
>
> **v2 (текущая версия).** Пересмотрено после ревью: архитектура из v1
> (отдельная сущность `CustomBuild`, отдельное хранилище `builds\`, отдельная
> мини-галерея) заменена на более простую — см. раздел 0.

## 0. Что изменилось относительно первой версии плана

Первая версия вводила отдельный тип сущности "сборка" (`CustomBuild`) со
своей галереей и своим редактором — по сути, второй параллельный пресет-стек
рядом с обычным. По итогам обсуждения это избыточно:

- **Нет отдельного типа сущности.** Смешивание — это свойство обычного
  `Preset`: у любого пресета (нового или уже существующего) отдельная роль
  может быть либо собственным файлом (как сейчас), либо ссылкой на роль
  другого пресета. Не нужен ни `CustomBuildStore`, ни `CustomBuildsGalleryWindow`,
  ни отдельная точка входа "Свой пресет" в галерее.
- **Нет отдельного редактора.** Используется тот же `PresetEditorWindow`,
  что и всегда — на каждом слоте появляется дополнительная кнопка
  "Выбрать из существующих" рядом с "Обзор...".
- **Бейдж вместо отдельной ячейки.** Пресет, у которого хотя бы одна роль —
  ссылка, помечается значком 🧩 в правом верхнем углу ячейки в общей
  галерее (не отдельная категория, просто визуальный маркер поверх обычной
  ячейки).
- **Ссылки "уплощаются" в момент выбора** (раздел 4.3) — при выборе роли из
  пресета, который сам содержит ссылки, реализация сразу разворачивает
  цепочку до конечного файла. Это устраняет необходимость в рекурсивном
  разрешении при каждом apply и делает циклы структурно невозможными.

## 1. Идея в двух словах

Пользователь хочет курсор-микс: роль `Arrow` — из пресета A, роль `Hand` —
из пресета B, и т.д. Обычный редактор пресета уже позволяет назначить на
слот произвольный файл с диска — но не даёт выбрать файл роли, которая уже
лежит внутри другого импортированного пресета (нужно было бы искать этот
файл на диске вручную, если он вообще доступен вне кэша приложения:
`%LOCALAPPDATA%\Cursor-Palette\presets\<id>\files\`).

Решение: на каждом слоте редактора, рядом с "Обзор...", кнопка **"Выбрать
из существующих"** — двухшаговый picker (пресет → роль внутри него),
результат которого — не копия файла, а ссылка `{presetId, fileName}`.

## 2. Модель данных

### 2.1 `Models/Preset.cs` — расширение существующего класса

```csharp
public sealed class Preset
{
    public required string Id { get; init; }
    public required string Name { get; set; }
    public DateTime CreatedAt { get; init; } = DateTime.Now;
    public int BaseSize { get; set; } = RegistryCursorService.DefaultBaseSize;

    public Dictionary<string, string> Roles { get; init; } = new();      // без изменений: role -> filename в СВОЕЙ files/
    public Dictionary<string, RoleRef> RoleRefs { get; init; } = new();   // НОВОЕ: role -> ссылка на чужую роль
}

public sealed class RoleRef
{
    public required string PresetId { get; init; }
    public required string FileName { get; init; }   // имя файла в files/ пресета PresetId
}
```

**Совместимость со старыми манифестами.** `RoleRefs` — новое поле с
дефолтным значением `new()`. У старых `manifest.json` (сохранённых до этой
фичи) поля `roleRefs` просто нет в JSON — `System.Text.Json` при десериализации
оставит дефолт (пустой словарь). Миграция не нужна, версионирование формата
не нужно.

**Инвариант ключей.** Один и тот же `registryName` не может одновременно
быть в `Roles` и в `RoleRefs` — при сохранении редактор пишет ровно один из
двух источников на слот (см. 3.3). `PresetStore.Save` должен явно удалять
ключ из другого словаря при пересохранении, если источник слота сменился
(например, роль была собственным файлом, стала ссылкой).

**Разрешение пути роли** — единственная точка входа для всего остального
кода (apply, превью в галерее, дефолтные пути в редакторе), правки только в
одном месте:

```csharp
// Services/PresetStore.cs
public static string? GetRoleFilePath(Preset preset, string registryName)
{
    if (preset.RoleRefs.TryGetValue(registryName, out var reference))
        return Path.Combine(GetFilesDir(reference.PresetId), reference.FileName);

    return preset.Roles.TryGetValue(registryName, out var fileName)
        ? Path.Combine(GetFilesDir(preset.Id), fileName)
        : null;
}
```

Это осознанно **простая замена** текущей реализации
(`Services/PresetStore.cs:18-21`) без сигнатурных изменений — значит,
все существующие вызовы уже "бесплатно" получают поддержку ссылок:
- `MainWindow.ApplyPreset` (`Views/MainWindow.xaml.cs:481-486`) — уже делает
  `File.Exists(path) ? path : EmptyValue`, то есть **битая ссылка уже
  сегодня приводит к безопасному fallback на дефолт**, без изменений кода.
- `MainWindow` — превью Arrow для ячейки галереи
  (`Views/MainWindow.xaml.cs:311-312`) и поиск активного пресета по
  сравнению путей Arrow (`Views/MainWindow.xaml.cs:597`) — работают как
  есть.
- `PresetEditorWindow` — подстановка уже сохранённых значений слотов при
  открытии существующего пресета (`Views/PresetEditorWindow.xaml.cs:86-91`)
  — тоже работает как есть, но см. 3.2 про то, что слоту дополнительно нужно
  знать, что источник — ссылка (для UI и для повторного сохранения без
  разрыва ссылки).

Единственное место, которое стоит доработать не строго обязательно, но для
консистентности — `Views/MainWindow.xaml.cs:311-312`, где фоллбэк "любая
заполненная роль, если Arrow пуст" сейчас перебирает только `preset.Roles.Keys`;
для пресета, где Arrow — ссылка, а остальные роли — тоже только ссылки,
`Roles` может быть пустым словарём. Нужно перебирать
`preset.Roles.Keys.Concat(preset.RoleRefs.Keys)`.

### 2.2 `Models/Preset.cs` — черновик (`PresetDraft`)

Текущий `PresetDraft.RoleSources` — `Dictionary<string, string>` (роль →
абсолютный путь файла на диске, который нужно скопировать). Меняется на:

```csharp
public sealed class PresetDraft
{
    public string? Id { get; set; }
    public string Name { get; set; } = "";
    public int BaseSize { get; set; } = RegistryCursorService.DefaultBaseSize;
    public Dictionary<string, RoleSourceDraft> RoleSources { get; init; } = new();
}

public sealed class RoleSourceDraft
{
    public string? OwnFilePath { get; init; }   // не null => обычный путь на диске, копируется как раньше
    public RoleRef? Ref { get; init; }           // не null => ссылка на чужой пресет (уже уплощённая, см. 4.3)
}
```

Единственный вызывающий код — `PresetEditorWindow.OnSaveButtonClick`
(`Views/PresetEditorWindow.xaml.cs:549-564`), см. 3.4.

### 2.3 `Services/PresetStore.cs` — `Save`, доработка

Текущий `Save` (`Services/PresetStore.cs:50-101`) построчно:
1. Для каждой пары `(role, sourcePath)` в `draft.RoleSources` — копирует
   файл в `files/`, пишет `roles[role] = fileName`.
2. Удаляет из `files/` всё, что не встретилось в новом `roles` (осиротевшие
   файлы после переназначения/удаления слотов).

Дорабатывается:
1. Ветка на тип `RoleSourceDraft`:
   - `OwnFilePath != null` — как раньше, плюс: если для этой роли раньше
     была ссылка (`existing.RoleRefs.ContainsKey(role)`) — не переносить её
     в новый `roleRefs`.
   - `Ref != null` — `roleRefs[role] = draft-е Ref` напрямую, без файлового
     I/O.
2. **Важно (иначе тихо ломает чужие пресеты): очистка осиротевших файлов
   должна учитывать ссылки из ДРУГИХ пресетов.** Сейчас шаг очистки
   (`Services/PresetStore.cs:80-86`) удаляет из `files/` этого пресета всё,
   что не входит в его же новый `roles.Values`. Но после этой фичи файл в
   `files/` пресета A может быть единственным физическим носителем для
   ссылки `{PresetId: A, FileName: F}` в пресете B (или даже в самом A, если
   роль X — ссылка на роль Y того же пресета). Наивная очистка удалит `F`,
   как только A перестанет держать `F` в собственном `Roles` — и молча
   оборвёт все ссылки на него, без предупреждения пользователю. Перед
   удалением файла как "осиротевшего" нужно проверить: не ссылается ли на
   `(A.Id, fileName)` хоть один `RoleRef` в `PresetStore.LoadAll()` (включая
   сам пересохраняемый пресет) — если да, файл не трогать. Стоимость —
   один проход по всем пресетам на каждое сохранение, для ожидаемых
   объёмов (десятки пресетов) незаметно.
3. Самоссылка разрешена и не требует спецкода: пресет может ссылаться сам
   на себя (`RoleRef.PresetId == draft.Id`) — например, продублировать файл
   роли `Hand` в роль `Pin` без похода на диск. Это просто ещё один пресет
   в списке в UI-picker'е (раздел 4.1) — не исключается из выбора.

### 3.4 Двухшаговый picker: `ExistingPresetPickerWindow` → `RolePickerWindow`

**Шаг 1 — выбор пресета-источника.** Новое окно `Views/ExistingPresetPickerWindow.xaml`:
сетка ячеек, визуально как основная галерея (превью Arrow, имя, счётчик
ролей) — источник данных `PresetStore.LoadAll()`, **без фильтрации** по
признаку "обычный/смешанный" — пресеты с бейджем 🧩 тоже валидны как
источник (явное требование: "можно открывать в том числе такие же
кастомные плитки тоже"). Клик по ячейке = выбор, `DialogResult = true`,
`ShowDialog()` из `PickExistingForSlot`.

Технически проще всего переиспользовать логику построения ячейки из
`MainWindow` (сейчас это приватный метод конкретного окна) — либо вынести
общий рендер ячейки в статический хелпер (`GalleryCellFactory` или
аналогично), либо просто продублировать урезанную версию (без
контекстного меню, без применения по клику) — решить на этапе реализации
по факту объёма дублирования.

**Шаг 2 — выбор роли/файла внутри выбранного пресета.** Новое окно
`Views/RolePickerWindow.xaml(.cs)`, принимает `(Preset source, string
currentRole)`:
- Тумблер **"Показывать только текущую роль"** — **включён по умолчанию**.
  - Включён: список сужается до одной карточки — файл роли `currentRole` в
    `source` (если она в нём заполнена — собственным файлом либо ссылкой,
    без разницы, отображается уже разрешённый файл через
    `PresetStore.GetRoleFilePath(source, currentRole)`). Если роль в
    источнике не заполнена — пустое состояние с текстом ("В этом пресете
    роль ‘Курсор ссылки’ не назначена").
  - Выключен: сетка карточек **по всем ролям** пресета `source`, у которых
    есть разрешённый путь (`PresetStore.GetRoleFilePath != null`) — превью
    + подпись роли (`Loc.Get("S." + role.DisplayKey)`), в любом порядке
    `CursorRoles.All`. Позволяет, например, взять курсор роли `Hand` из
    чужого пресета и назначить его на свою роль `Pin` — намеренно
    разрешено, кросс-ролевое назначение уже штатно поддерживается обычным
    "Обзор..." (можно и сейчас подсунуть произвольный файл на любой слот),
    здесь то же самое, просто источник — не диск, а чужой пресет.
- Клик по карточке → `RolePickerWindow` возвращает выбранную пару
  `(pickedRole: string, ...)`; сам компонент, вызывающий picker
  (`PickExistingForSlot`, раздел 3.5), берёт из неё не "роль", а сразу
  готовую ссылку на физический файл — см. уплощение в 4.3.

### 3.5 `PickExistingForSlot` — точка сборки шагов 1 и 2

```csharp
private void PickExistingForSlot(Slot slot)
{
    var presetPicker = new ExistingPresetPickerWindow(PresetStore.LoadAll()) { Owner = this };
    if (presetPicker.ShowDialog() != true)
        return;

    var rolePicker = new RolePickerWindow(presetPicker.SelectedPreset!, slot.Role.RegistryName) { Owner = this };
    if (rolePicker.ShowDialog() != true)
        return;

    var flatRef = ResolveLeafRef(presetPicker.SelectedPreset!, rolePicker.SelectedRole!);
    if (flatRef == null)
        return;   // выбранная роль в источнике внезапно оказалась без файла (гонка/битая ссылка) — молча отменить выбор

    SetSlotReference(slot, flatRef.PresetId, flatRef.FileName);
}
```

## 4. Уплощение ссылок ("flatten on pick")

### 4.1 Зачем

Если бы `RoleRef` мог указывать на роль, которая сама является `RoleRef`
(цепочка A → B → C), пришлось бы либо разрешать её рекурсивно при каждом
apply (лишняя работа + риск случайного цикла при повреждённых данных), либо
специально защищаться от циклов. Вместо этого — инвариант: **`RoleRef`
всегда указывает на пресет, где выбранный файл лежит в его собственном
`Roles` (не в его `RoleRefs`)**. Раз инвариант держится с первого же
сохранения — циклов и многошаговых цепочек не может возникнуть
структурно, без отдельной проверки.

### 4.2 Соблюдение инварианта

Инвариант поддерживается в одной точке — в момент, когда пользователь
выбирает роль во `RolePickerWindow` (раздел 3.4, шаг 2), **до** того как
значение попадёт в `Slot`/`PresetDraft`. Реализация:

```csharp
// Services/PresetStore.cs (или отдельный статический хелпер рядом)
public static RoleRef? ResolveLeafRef(Preset source, string registryName)
{
    if (source.RoleRefs.TryGetValue(registryName, out var existingRef))
        return existingRef;   // уже уплощена при сохранении source — переносим как есть, без похода вглубь

    return source.Roles.TryGetValue(registryName, out var fileName)
        ? new RoleRef { PresetId = source.Id, FileName = fileName }
        : null;
}
```

Поскольку `source.RoleRefs` **уже** гарантированно уплощена (по индукции —
она была уплощена в момент, когда сохранялся `source`), достаточно одного
уровня — рекурсия не нужна.

### 4.3 Итог инварианта

`RoleRef.PresetId` всегда указывает на пресет, у которого
`Roles[?] == RoleRef.FileName` для какой-то роли — то есть на физического
владельца файла. Это же значение используется в `PresetStore.GetRoleFilePath`
(раздел 2.1) без какой-либо рекурсии.

## 5. Крайние случаи

### 5.1 Удаление пресета-источника

`PresetStore.Delete` (`Services/PresetStore.cs:125-131`) ничего не знает о
ссылках и не обязано — удаление стирает `presets\<id>\`, любые `RoleRef`,
указывающие на этот `id`, автоматически становятся битыми. `GetRoleFilePath`
вернёт путь к несуществующему файлу → существующий код (`File.Exists`
проверки на местах вызова, раздел 2.1) уже трактует это как "роль пуста",
без падений.

Опционально (не в MVP-версии фичи, полировка): при удалении пресета
проверить `PresetStore.LoadAll()` на наличие `RoleRefs`, указывающих на
удаляемый `id`, и предупредить пользователя списком затронутых пресетов —
не блокирует удаление, чисто информативно.

### 5.2 Осиротевшие файлы при пересохранении (см. 2.3, п.2)

Уже разобрано выше — при сохранении пресета его собственные файлы, на
которые ссылаются другие пресеты, не должны удаляться, даже если сам
пресет-владелец больше не держит их в своём `Roles`. Это единственное
по-настоящему обязательное изменение существующей логики (не просто
аддитивное расширение) — без него фича будет молча ломать чужие пресеты
при обычном редактировании.

### 5.3 Переименование файла роли при пересохранении источника

Если пользователь в пресете-источнике заменяет файл роли на другой файл с
другим именем (не тем же самым) — старое `FileName`, на который были
ссылки, больше не входит в `Roles.Values`, значит правило 5.2 его не
защитит (защита срабатывает только для файлов, на физическое содержимое
которых ссылаются другие; если сам файл роли **заменён**, а не просто
"освобождён", это уже не тот же файл — старый закономерно удаляется как
осиротевший, ссылки на него становятся битыми). Это штатное, ожидаемое
поведение (аналогично 7.3 из v1 плана) — отдельной защиты не требуется,
риск объясняется пользователю только тем, что редактирование пресета может
повлиять на пресеты, которые из него что-то заимствуют (см. 5.1 про
опциональное предупреждение).

### 5.4 Самоссылка и кросс-ролевые ссылки

Разрешены явно (см. 2.3 п.3 и 3.4) — не крайний случай, а штатная
возможность.

## 7. План реализации (по шагам)

1. **Модель + хранилище**: `RoleRef` в `Models/Preset.cs`, обновлённый
   `PresetDraft`/`RoleSourceDraft`, доработка `PresetStore.GetRoleFilePath`
   и `PresetStore.Save` (включая защиту осиротевших файлов, раздел 5.2) —
   без UI, проверяется вручную (создать пресет со ссылкой через код/тест,
   убедиться, что apply подтягивает верный файл).
2. **Бейдж в галерее** (раздел 3.2) — можно сделать сразу после шага 1 и
   протестировать на вручную слепленном манифесте с `roleRefs`, до готовности
   UI выбора.
3. **`RolePickerWindow`** (шаг 2 picker'а, раздел 3.4) — можно собрать и
   проверить отдельно, передавая ему пресет напрямую из кода.
4. **`ExistingPresetPickerWindow`** (шаг 1 picker'а) + кнопка на слоте
   (раздел 3.3) + `PickExistingForSlot` (раздел 3.5) — соединяет всё в
   рабочий сквозной сценарий.
5. **Полировка**: тултип на бейдже, опциональное предупреждение при удалении
   используемого пресета (5.1), локализация (раздел 6).
